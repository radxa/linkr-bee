# Agent 优化与实机验收

## 软件行为

输入快捷键：`⌘/Ctrl + Shift + K` 打开并聚焦 Agent；`⌘/Ctrl + Enter` 发送；普通 Enter 换行。中文输入法组合输入期间不会触发这些快捷键。箭头按钮保留可访问的“发送”名称，悬停可查看发送快捷键。

- **任务记录与设备**：按 BLE 设备 ID / WebSocket 地址和 UART 设置隔离，最多保存 20 个任务摘要。刷新后运行中的摘要显示为中断。点击“核实上次任务”只填入问题，提交后必须先读取当前设备状态与串口日志，下一轮才能申请新动作。不会恢复旧命令队列或授权。
- 记录仅保存目标、回答摘要及最多 8 条执行结果元数据，不保存可重发命令和模型配置。常见凭据格式及 URL 查询参数做脱敏，但自由文本仍可能包含设备信息；可以清除当前设备记录。存储失败会提示。
- **探测设备**：使用 `probe_device_profile` 读取 OS、板型、boot ID、根文件系统容量和工具路径是否存在。沿用执行档位的审批规则；成功的完整输出才生成档案。档案为当前会话内观测值，重连后清空，识别重启、日志丢失或超过 15 分钟后标为过期。串口无法可靠识别所有自定义重启输出，操作前仍需核实目标。
- **交互**：识别 sudo 密码、密码、登录、确认和分页提示；监视工具遇到等待输入立即返回。密码由用户直接在终端输入。提示识别是启发式观察，不授予自动执行权限。
- **执行记录**：显示命令、耗时、传输状态、退出码、下载元数据；日志可展开，命令与 Markdown 代码支持复制。退出码不代表最终目标验证通过。
- **上下文**：增量读取日志；旧证据压缩时保留头尾及选取的错误行，机械摘要去重；保留当前问题和合法工具调用/结果配对。不引入额外摘要模型调用。

## AI 设置中的目标机绑定

AI 设置现在提供核实、绑定、解除和重新生成入口。通过 BLE 管理通道使用 `@linkr target?`、`@linkr target=<UUID>`、`@linkr target clear`；固件把目标 UUID 保存到 settings 的 `linkr_target/v1`，相同值不重复写入。UUID 是关联标识，不是目标机身份认证凭据。

绑定在目标机 `/var/lib/linkr/device-id` 创建 UUID，已有合法 UUID 保留；重新生成必须勾选允许替换，以临时文件加重命名更新。操作要求已登录的 POSIX Shell。优先读取已有系统 ID，其次读取用户目录 ID；首次创建优先尝试系统目录，必要时通过 sudo 提权，用户直接在串口输入密码。sudo 不可用或失败时回退到 `~/.local/share/linkr/device-id`（随登录用户变化）。已有系统文件读取失败或不合法时不另建身份。出现密码提示后本次自动核实暂停，命令结束后需再次点击绑定重新读取 ID；不采集或自动输入密码。读取普通文件、命令成功及 UUID 格式全部确认后才请求 Bee 保存。没有 Bee 成功响应、断连或日志不完整都不能视为绑定成功；目标机文件可能已写入，恢复后先核实，不自动重放。

解除只清除 Bee 关联。核实成功后任务历史改用目标 UUID 作为索引，已探测档案以历史信息保存到当前浏览器；动态状态仍需按需核实。重连取消本次核实状态，用户可用“核实绑定”读取一次 ID。旧的 Bee/地址索引历史不自动迁移，避免错误关联。

初期验证：主机设置存储桩测试与模拟 BLE/UART 浏览器测试覆盖正常及失败路径。当时尚未完成实际 Flash 写入或真实目标机绑定；后续实机结果见下文。

连接后，在本次会话观察到空闲 Shell 时自动核实一次目标身份：查询 Bee 绑定并只读取目标 ID 文件；没有绑定时不发送串口探测。只有 UUID 匹配才加载浏览器中对应的历史能力档案；登录/密码提示、ID 缺失、不匹配或输入被打断都不授权历史档案，也不自动循环探测。Agent 使用 `probe_tools` 按任务检查所需命令；完整设备探测仅用于未知目标或明确的全面调查。实时磁盘空间、网络和进程仍需按任务重新读取。

## 2026-09-18 可机器判定的验证

新增 `verify_target_file` 与 `verify_target_service`：这两个工具的结论由**应用**比对目标机回答与调用方预期得出，不由模型读输出判断。

- **状态语义**：`match`（给定预期全部成立）/ `mismatch`（至少一项不符，或可证明不是预期的东西）/ `indeterminate`（目标机答不了或回答不可用，两种情况都不作断言）/ `observed`（没有给预期值，只是测量，不构成校验）。`observed` 与 `match` 的区别是关键：没有预期值时不会返回 `match`。
- **`verify_target_file`**：存在性、类型、字节数、sha256。`sha256` 与 `bytes` 任给其一即为校验，都不给则为测量（或显式 `hash: true` 只取摘要）。只依赖 POSIX `wc`；sha256sum 与 shasum 都不存在时返回 `indeterminate` 并说明原因，不会静默通过。
- **`verify_target_service`**：`unit` / `process` / `port` 三选一。`expect` 可选，默认分别是 `active` / `running` / `listening`。**单元不存在（`LoadState=not-found`）返回 `indeterminate` 而不是"已停止"**；目标机没有 systemctl / pgrep / ss 时返回 `indeterminate` 并给出 `unsupported` 原因。
- **证据纪律**：每个结果都带 `source: "application-verification"`、产生它的命令、执行 id、判定所依据的标记行，以及一条明确否定过度解读的说明（`match` 只证明给定预期成立，不代表用户目标达成）。
- **误报防护**：控制台证据是共享日志的窗口，先前一次校验别的路径的输出可能还在其中，因此命令先回显被校验对象、解析器比对后才认账；命令回显不构成输出（标记只按整行匹配）。`denied` / `unreadable` 只说"内容没看到"，不声称字节不符。

验证方式：

- 模块层 `mobile/test/target_verify.test.mjs` 12 项：除命令形状与参数校验外，把生成的命令交给 `/bin/sh` 在真实文件系统上执行；服务路径用放进 `PATH` 的 `systemctl` / `pgrep` / `ss` 桩固定回答，因此"目标机缺少该工具"也被确定性覆盖。含 CRLF、`wc` 前导空格、回显不构成输出、跨请求归因。
- 工具层 `mobile/test/verify_tools.test.mjs` 5 项：裁决归属、`mismatch` 不被洗成成功、答不了时如实给 `indeterminate`、无法处理的请求报错而不静默通过。假目标机把命令回显写进日志，同时验证回显骗不过解析器。
- 主机回归 270 项全部通过；`npm run build`（含 `tsc --noEmit`）通过；`web/vendor/agent/` bundle 已重新生成，摘要一致性测试通过。bundle 体积 1020325 字节（原 1002329），按需加载，不影响终端首屏。

## 2026-09-18 静态路径回归（推翻上一节的结论）

上一节把 `static_agent.spec.mjs` 的 3 项失败判为"本机环境问题"就收手了。**那个判定是错的**：它只证明了"不是我改的"，没有证明"没法修"。

根因定位：

- 隔离实验（把静态服务器和 Chrome 放在同一个进程里）：Node `fetch` 与 Chrome 访问 `http://127.0.0.1:8766/` 均返回 **200**，服务器本身没问题。
- 在**同一条命令内**先手动起好静态服务器、再跑 Playwright（走 `reuseExistingServer` 复用分支）：那 3 项 **3 passed**。
- 结论：问题出在 **Playwright 自己 spawn 第二个 `webServer` 条目**上——它起不来，而 Playwright 认为它已就绪，于是页面拿到连接拒绝。

修法（`browser-test/static_agent.spec.mjs` + `playwright.config.mjs`）：删掉配置里的第二个 `webServer` 条目，改由该 spec 在 `beforeAll` 里**自己启动**静态服务器（即复现上面"通过"的那个条件），`afterAll` 关闭；端口上已有服务器则复用；启动失败在超时后**以明确原因让整个文件失败**，不静默跳过。

顺带修掉一处误导性报错：`web/agent_runtime.js` 原先把动态 import 的失败原因吞掉，任何加载失败都报成"bundle 缺失或不可读，请重新构建"。现在真实原因随消息一起给出——这个 import 可能因与 bundle 新旧无关的原因失败（语法有效但无法加载、服务器 Content-Type 不对、抓取被拒），原提示会把读者引向错误方向。

**这一改动本身尚未被真正验证过**：改完之后那次运行直接通过了，改进后的消息没有再显示过。它是按"报错要说实话"的一般原则做的，等下一次静态路径真的失败时才会体现价值——真失败时应当先看这句话里的原因，而不是直接去重建 bundle。

结果：**164 项全部通过**（本会话首次全绿）。同轮复测中 `agent_governance.spec.mjs` 有一项在整套运行时失败、单独复测 6 项全过，属 flake——**没有**把它算作通过，如实记录。

## 2026-09-18 上下文预算与固定开销

测量起点：**系统提示词 + 全部工具描述每一次模型调用都要发一遍**。实测 13,661 字符 + 24 个工具 8,983 字符 = 22,644 字符 ≈ 6,290 token（3.6 字符/token）≈ 默认 32K 窗口的 19%。

| 用户设置 | 固定开销 | 历史最多 | 合计 | 结果 |
| --- | --- | --- | --- | --- |
| 32768（默认） | 6,290 | ~6,700 | ~13,000 | 剩余约 60%，正常 |
| 8192 | 6,290 | ~6,700 | ~13,000 | **超出 1.6 倍** |
| 4096 | 6,290 | ~6,700 | ~13,000 | **超出 3.2 倍** |
| 1000（允许的最小值） | 6,290 | — | — | 光固定开销就超 6 倍 |

修法与验证：

- 预算改为 `contextBudgetChars()` 从窗口推导：窗口 − 固定开销（3 字符/token）− 输出预留 − 帧开销，再按 2 字符/token 折成字符；上限仍为 24000，**因此大窗口行为不变**（`contextBudgetChars(32768, 实测固定开销, 4096)` 仍等于 24000）。
- 预算按每次压缩时生效的工具列表计算（工具解锁会改变固定开销）；`prompt()` 里压缩与刷新系统提示词的顺序理正。
- 设置界面在窗口过小时给出带具体数字的警告（不再只在表单脏时才提示——它描述的是已保存配置的属性）。
- 主机回归 **276 项全部通过**（新增 6 项）；`npm run build`（含 `tsc --noEmit`）通过；bundle 已按新源重新生成。
- 新增防漂移测试：重新测量真实提示词与工具描述，超过 `AGENT_FIXED_CONTEXT_TOKENS` 即失败。当前保守估计 7,548 token，常数 8,000，留有约 450 token 余量；一旦有人加一个很长的工具描述就会失败并提示更新常数。
- 工具描述压缩：9,402 → 8,983 字符（约 −120 token）。**收益很小，如实记录**；保留的价值是上面那项防漂移测试。

未覆盖：历史里没有 assistant 消息时无法构造摘要，压缩会原样返回（超预算也不收缩）。这种历史实际只有零星几条用户消息，远小于固定开销，边界很窄。另外字符/token 换算用的是保守常数而非真实分词器——应用里没有可用的分词器，所以宁可低估预算。

## 2026-09-29 Pages 上的 LAN 桥：一个被实测推翻的结论

我一度判断"部署到 GitHub Pages 后 LAN（局域网 WebSocket 桥）必然连不上，因为 https 页面不允许 `ws://`"，并据此做了一套构建开关把 LAN 入口隐藏掉。**这个判断是错的，相关改动已回退。**

实测（2026-09-29，从 `https://radxa.github.io/linkr-bee/` 页面本身发起，Chrome）：

| 目标 | 结果 |
| --- | --- |
| `ws://127.0.0.1:8799/ws` | 连接成功 |
| `ws://localhost:8799/ws` | 连接成功 |
| `ws://192.168.2.151:8799/ws`（局域网地址）| 连接成功 |
| `ws://192.168.8.216:8799/ws`（局域网地址）| 连接成功 |

浏览器确实打印 mixed-content 提示，但那是 **warning 而不是拦截**，原文：`Mixed Content: ... attempted to connect to the insecure WebSocket endpoint 'ws://192.168.2.151:8799/ws'. This endpoint should be available via WSS. Insecure access to this endpoint is deprecated.`，并附 `Connecting to a non-secure WebSocket server from a secure origin is deprecated.`

所以准确的说法是：**Chromium 目前允许 https 页面连接 `ws://`（含局域网地址），只是标注为已弃用。** 而用户提的直觉是对的——设备联网设置（WiFi 卡片）走的是 `@w=` 命令经串口（BLE 模式），本来就不受影响，与 `ws://` 无关。

补充一条推论：这个终端依赖 Web Bluetooth，只有 Chromium 系浏览器支持（Safari / Firefox 都不支持），而 Chromium 正是目前放行 `ws://` 的浏览器——**能跑这个应用的用户，今天两种传输方式都能用**。

回退做法：`git revert` 掉该提交（移除 `web/build_flags.js`、`tools/build_pages.sh`、`build.yml` 里对它的语法检查、Pages 变体用例，以及 `app.js` / `style.css` 中为隐藏而加的改动），Pages 恢复直接发布 `web/`。**同一批里的两个真实修复保留**：1 MB bundle 动态 import 的重试与真实报错，以及测试服务器的 worker 归属修复（`test.describe.configure({ mode: "serial" })`）。

教训：**"浏览器会拦 `ws://`"这类断言必须实测**，尤其是在我准备据此**去掉一个能用的功能**时。查规范、凭记忆都不如跑一次测量。

### 一处我判错两次的结论，与真正的根因

`static_agent.spec.mjs` 的最后一个用例偶发 `ERR_CONNECTION_REFUSED at http://127.0.0.1:8766/`。我先后把它归因为"本机环境问题"和"本地 flake"，**两次都错**：CI 上同样复现（`an unreachable endpoint explains the browser-side conditions`），这才排除环境。

真正原因是 harness 设计错误——**Playwright 的 `beforeAll`/`afterAll` 只在同一个 worker 内生效**：文件被拆到两个 worker 时，worker A 结束时执行 `afterAll` 杀掉它启动的 8766 服务器，而 worker B 复用了该服务器、并不持有它 → 连接拒绝。修法是给该文件加 `test.describe.configure({ mode: "serial" })`：服务器是**文件级** fixture，不该被拆开。

教训写在这里而不只写在提交信息里：**"偶发"不等于"环境"**，先问"这个失败能不能用我自己的代码解释"；而且**重试会把这类 bug 藏起来**——当时给动态 import 加重试，差点就掩盖了它。

另一处独立修复：1 MB 的 bundle 动态 import 偶发取回失败，会让终端在没有助手的状态下卡住。现在重试一次，并让错误带上真实原因——正是这条原因把上面那个 bug 暴露了出来。

Validation: 284 node tests, 165 browser tests, both web builds, CI 7/7 jobs（含 4 块板）。真机行为未测。
