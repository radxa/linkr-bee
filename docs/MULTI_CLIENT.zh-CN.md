# 多客户端串口会话

[English](MULTI_CLIENT.md) | [开发指南](DEVELOPMENT.zh-CN.md)

## 本阶段范围

默认构建允许两台 BLE 主机同时在线，所有已授权客户端共享同一份 UART 输出，
但同一时刻只有一个会话可以输入或修改配件设置。BLE 与已认证的局域网客户端
共用控制权，不能从另一种通道绕过只读限制。这不是多套独立 shell 或用户隔离。
只读客户端也能看到共享控制台，因此仍应仅给可信设备配对。

Linkr 固件端适配及可信 Linkr 身份绑定暂不实现。状态明确返回
`linkr_reserved=0`，本阶段不锁死空槽，两台现有客户端均可使用。
未来专用名额必须基于已授权的配对身份，不能凭广播名称或客户端自报角色判断。

## 客户端交互

Web 和移动端共用页面检查能力位 bit 7。连接后先查询控制权，无人控制时自动申请；
其他会话对自动任务保持只读，但终端仍可输入：第一次按键会请求**空闲交接**，当前控制端
安静超过 `CONFIG_LINKR_BLE_BRIDGE_SESSION_IDLE_MS`（默认 3 秒）时自动接过控制权并发送
这次输入。“申请控制”按钮是抢占路径，会立即生效，即使对方正在输入。控制端可“释放”，
不必断开连接；释放后的下一次人工输入可以重新取回。状态每两秒刷新。鸿蒙外壳复用该页面。

键盘、终端自动应答、快捷命令、AI 执行、UART 设置及远端终端尺寸同步均跟随控制权；
唯一的例外是人工按键可以触发上述空闲交接。旁观端调整本地窗口不会发送 `stty`，丢失
控制权时取消旧的待发送任务。

未使用新控制权 API 的旧客户端，可以用首次 UART 写入或修改管理指令取得空闲控制权；
当前控制端安静超过空闲窗口后也会被接管，但不能在对方持续写入时插入。旧 CLI/TUI 暂无
专门的控制状态按钮，但首次写入同样享受空闲规则。

## 协议

Management v1 帧格式与请求编号不变，新增 bit 7 `MULTI_SESSION`：

| 指令 | 行为 |
| --- | --- |
| `@c?` | 查询本会话编号、控制端及容量 |
| `@c claim` | 立即取得控制权，可抢占正在输入的会话 |
| `@c claim idle` | 仅当当前控制端安静超过空闲窗口时取得控制权 |
| `@c release` | 控制端释放控制权 |
| `@c yield 2` | 控制端主动交接给在线会话 2 |
| `@c ai on <epoch>` / `@c ai off <epoch>` | 当前控制端通知 AI 开始／结束，不改变控制权 |

长格式为 `@linkr control?` 和 `@linkr control <动作>`。

```text
OK control self=2 owner=1 mode=readonly epoch=3 peers=2 ble_max=2 linkr_reserved=0 agent_led=1
```

`mode` 分别为 `control`、`readonly`、`available`；会话编号只在本次连接有效。
`peers` 包括 BLE 和 LAN，`ble_max` 单独表示 BLE 容量。控制权改变时 `epoch` 递增。
失败会返回 `control=busy`（空闲申请时对方仍在输入）、`not_owner`、`bad_peer`、
`bad_action`、`disconnected` 或 `readonly`。空闲窗口由 Kconfig
`LINKR_BLE_BRIDGE_SESSION_IDLE_MS` 控制（默认 3000 毫秒）；每次被接受的 UART 写入或
管理修改都会刷新控制端活动时间，已经排队的字节仍由 epoch 保护。

LAN 认证不变。新固件在认证完成后主动发送文本状态帧；客户端收到该能力声明后，
才可发送 `@control ?`、`@control claim`、`@control release` 或 `@control yield 2`
文本帧。UART 必须使用二进制帧；文本帧保留给控制协议，分片或超长控制帧会被拒绝，
不能泄漏到 SBC。不要对旧版 LAN 固件发送探测控制文本。

`agent_led=1` 声明支持 AI 状态通知。客户端只在该字段存在时发送通知，并带上
当前 `epoch`；旧代际返回 `stale_epoch`，非控制端返回 `not_owner`。Web／移动端／
HarmonyOS 助手和常驻任务开始时发送 `ai on`，每 2 秒续期，结束或停止时发送 `ai off`。
心跳不刷新串口控制权的空闲计时。释放、交接、断连立即撤销 AI 状态，丢失心跳后
15 秒自动恢复连接状态色；普通 `claim` 不代表 AI 接管。LAN 使用同样的
`@control ai on <epoch>`／`@control ai off <epoch>` 文本帧。该通知不写入 NVS。

## 队列和交接边界

每个 BLE 连接独立维护接收组帧、序号、NUS/Reliable 选择、管理响应、输出队列及发送线程。
显式 CCC 写入只选择对应连接的通道；恢复的历史 CCC 不覆盖后续显式选择。
一台设备断开不会清空另一台的请求或数据。输出队列满时**不会**断开慢客户端：桥接器
只丢这一块数据、累计丢失字节数（`linkr_ble_peer_dropped()`）并保持连接——断开连接会
把一阵串口输出变成一台"死掉"的终端。丢包日志最多每秒一条；目标侧的 UART 环形缓冲
同样按这种语义丢数据，而不是拖住 UART 采集。

UART 输入队列和待执行的修改指令附带控制代际。释放、交接或掉线会使旧排队任务失效。
已经交给唯一 UART 发送线程的在途数据不能撤回，会先发完再处理下一包；已经接受的
异步操作也可能继续完成。交接不会自动注入 Ctrl-C，也不会清空 SBC 尚未执行的命令行，
新控制端仍然是在接管同一份串口会话。

## 构建和实机验收

默认两连接；三连接通过实验配置启用，并收紧每连接缓冲：

```sh
west build -d build-three -b esp32c3_supermini . -- -DEXTRA_CONF_FILE=multi3.conf
```

该实验配置只在 C3 上做构建验证。完整功能的 C5/WROOM 内部 SRAM 余量很小，
本阶段保持两连接，不应直接套用三连接配置。

主机控制权测试（包括抢占 `claim`、空闲 `claim idle` 与无感写入交接）通过，
C3、C5 与 `linkr_bee_x1_0` 固件均以 3000 ms 默认值构建成功。X1.0 镜像使用固定的
`linkr_multipeer_zephyr` 工作区构建，因为默认工作区的 simple-boot loader 已包含
仓库 shim 正在防护的上游 digest 变化。

编译、主机测试不等于实机验收。发布前需验证两台真实主机、第三台接入、不同 MTU 和
通道、配对重连、控制权交接、慢客户端、持续串口日志、GPIO 配对门禁及 WiFi 共存。
逐板检查栈水位、运行时堆、队列丢失和看门狗重启，三连接不能仅凭链接成功宣称稳定。
